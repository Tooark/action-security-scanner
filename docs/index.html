01

O que é — e o que não é

O scanner de verdade mora em outro repositório. Aqui está só a configuração de CI que o invoca, versionada e publicada como se fosse um pacote.

O scanner é uma imagem Docker publicada a partir de Tooark/base-images como {{SCANNER_IMAGE}}:{{SCANNER_VERSION}}. Dentro dela existe um CLI chamado ark-tools, que orquestra três ferramentas e produz um relatório JSON no formato {{REPORT_SCHEMA}} v{{REPORT_VERSION}}.

Este repositório resolve um problema diferente e bem específico:

O problema

“Temos 40 projetos. Não quero copiar 80 linhas de YAML de segurança em cada um deles, e quando o scanner mudar não quero editar 40 arquivos.”

Em vocabulário de desenvolvimento: este repositório é uma biblioteca, e os projetos que a consomem são os dependentes. A tag v{{COMPONENT_VERSION}} é a versão do pacote. Quem consome não copia código — declara uma dependência.

Uma fachada, um motor e um projeto irmão

A biblioteca tem duas peças. O que ela promete a quem consome é que todo input documentado faz o que a documentação diz — e o resto do repositório, de scripts/ a tests/, existe para impedir que essa promessa se perca com o tempo.

Peça Arquivo Papel
Fachada action.yml Composite Action: declara inputs e outputs e encadeia os passos
Motor src/run-scanner.sh Traduz os inputs em um docker run da imagem

Os mesmos scans existem para GitLab CI em um repositório irmão, Tooark/template-ci-security-scanner, com os mesmos nomes de input em snake_case. É por isso que os inputs daqui seguem o nome da variável que a imagem lê, em kebab-case: TRIVY_SEVERITY é trivy-severity aqui e trivy_severity lá, e quem troca de plataforma não precisa reaprender nada.

What it is — and what it is not

The scanner itself lives in another repository. What is here is only the CI configuration that invokes it, versioned and published as if it were a package.

The scanner is a Docker image built from Tooark/base-images and published as {{SCANNER_IMAGE}}:{{SCANNER_VERSION}}. Inside it there is a CLI called ark-tools that orchestrates three tools and produces a JSON report in the {{REPORT_SCHEMA}} v{{REPORT_VERSION}} format.

This repository solves a different and very specific problem:

The problem

“We have 40 projects. I do not want to copy 80 lines of security YAML into each of them, and when the scanner changes I do not want to edit 40 files.”

In development vocabulary: this repository is a library, and the projects that consume it are its dependents. The tag v{{COMPONENT_VERSION}} is the package version. Consumers do not copy code — they declare a dependency.

A front end, an engine and a sister project

The library has two parts. What it promises a consumer is that every documented input does what the documentation says — and the rest of the repository, from scripts/ to tests/, exists to stop that promise from eroding over time.

Part File Role
Front end action.yml Composite Action: declares the inputs and outputs and chains the steps
Engine src/run-scanner.sh Turns the inputs into a docker run of the image

The same scans ship for GitLab CI from a sister repository, Tooark/template-ci-security-scanner, with the same input names in snake_case. That is why the inputs here follow the name of the variable the image reads, in kebab-case: TRIVY_SEVERITY is trivy-severity here and trivy_severity there, and someone moving between the two platforms has nothing to relearn.

02

Os conceitos de CI, em termos de dev

Cinco termos destravam a leitura de qualquer arquivo deste repositório.

Termo O que é Analogia
Pipeline
/ Workflow		 Tudo que roda quando você dá push A main() do build
Job Unidade isolada de trabalho, em um container ou VM limpa Uma função — roda em processo próprio
Step Um passo dentro de um job: um comando ou uma Action. Os passos rodam em sequência, no mesmo disco Uma chamada dentro da função — é onde esta Action entra
Runner A máquina que executa o job O servidor onde o processo roda
Artifact Arquivo que o job produz e que sobrevive ao fim dele Valor de retorno persistido

Dois detalhes explicam grande parte do código deste repositório.

Um job começa do zero toda vez

Container novo, disco vazio. É por isso que existe cache — sem ele, o Trivy baixaria um banco de vulnerabilidades de centenas de megabytes a cada execução. O cache é o assunto de boa parte do action.yml.

Um job “falha” quando o comando sai com exit code diferente de zero

É assim que um scanner bloqueia um merge: ele encontra uma CVE crítica e retorna 1. Isso se chama failure gate, e boa parte dos inputs deste projeto existe só para você escolher quando o portão fecha.

Trivy

Falha quando uma severidade listada em trivy-severity-fail tem correção disponível.

desligar → trivy-exit-code: "0"

Hadolint

Falha a partir do nível definido em hadolint-failure-level.

desligar → hadolint-failure-level: "none"

Betterleaks

Falha quando qualquer segredo é detectado.

desligar → betterleaks-fail-on-findings: "false"

Existe um meio-termo: soft-fail: "true" transforma qualquer gate no output exit-code em vez de derrubar o passo — útil para adotar o scanner em um projeto legado sem travar todo mundo no primeiro dia.

CI concepts, in dev terms

Five terms unlock reading any file in this repository.

Term What it is Analogy
Pipeline
/ Workflow		 Everything that runs when you push The build's main()
Job An isolated unit of work, in a fresh container or VM A function — runs in its own process
Step One step inside a job: a command or an Action. Steps run in sequence, on the same disk A call inside the function — where this Action fits
Runner The machine that executes the job The server the process runs on
Artifact A file the job produces that outlives it A persisted return value

Two details explain much of the code in this repository.

A job starts from nothing every time

New container, empty disk. That is why caching exists — without it Trivy would download a vulnerability database of hundreds of megabytes on every run. The cache is the subject of a good part of action.yml.

A job “fails” when the command exits non-zero

That is how a scanner blocks a merge: it finds a critical CVE and returns 1. This is called a failure gate, and much of this project's input surface exists only so you can choose when the gate closes.

Trivy

Fails when a severity listed in trivy-severity-fail has a fix available.

turn off → trivy-exit-code: "0"

Hadolint

Fails at or above the level set in hadolint-failure-level.

turn off → hadolint-failure-level: "none"

Betterleaks

Fails when any secret is detected.

turn off → betterleaks-fail-on-findings: "false"

There is a middle ground: soft-fail: "true" turns any gate into the exit-code output instead of failing the step — useful for adopting the scanner in a legacy project without blocking everyone on day one.

O que o scanner realmente roda

Três ferramentas com escopos que não se sobrepõem, e sete comandos que as combinam.

Ferramenta Procura Exemplo de achado
Trivy Vulnerabilidades (CVEs) em dependências, imagens Docker e configs de infraestrutura log4j 2.14 → CVE-2021-44228, CRITICAL
Hadolint Más práticas em Dockerfile Uso de :latest, container rodando como root
Betterleaks Segredos vazados no código e no histórico do git Uma chave AWS commitada e “removida” três commits depois

Comando O que escaneia Ferramenta

What the scanner actually runs

Three tools with non-overlapping scopes, and seven commands that combine them.

Tool Looks for Example finding
Trivy Vulnerabilities (CVEs) in dependencies, Docker images and infrastructure config log4j 2.14 → CVE-2021-44228, CRITICAL
Hadolint Dockerfile bad practice Using :latest, a container running as root
Betterleaks Secrets leaked in the code and in the git history An AWS key committed and “removed” three commits later

The seven commands

Command What it scans Tool
full-scan Everything at once: image + source + secrets + Dockerfile, merged into one report all three
image-scan A Docker image Trivy
filesystem-scan Source dependencies (lockfiles, OS and language packages) Trivy
config-scan IaC and config: Terraform, Kubernetes, and so on Trivy
repo-scan A repository — including a remote one, by URL Trivy
dockerfile-lint One Dockerfile Hadolint
secret-scan Secrets in the working tree and in the history Betterleaks

All seven are a single Action, selected through the command input; full-scan is the default. An Action is a step inside a job that already exists, so running two scans means writing two steps.

Reports land in scan-reports/ and are uploaded as an artifact. full-scan also writes the consolidated full-scan-report.json.

05

A fachada: action.yml

Uma composite Action é uma Action feita de outras Actions e comandos shell, sem código compilado.

Quando alguém escreve uses: Tooark/action-security-scanner@v{{COMPONENT_VERSION}}, o GitHub baixa este repositório e executa os passos declarados aqui dentro do job de quem chamou. O arquivo tem quatro blocos.

inputs: — os parâmetros

São 45, cada um com description e default. Pense neles como a assinatura de função pública da biblioteca: é o contrato com quem consome, e mudá-los quebra gente. 

trivy-severity:
  description: "Severities included in the report, e.g. CRITICAL,HIGH."
  required: false
  default: ""

A maioria tem default: "". Isso não é preguiça — é a regra de precedência, explicada em Decisões.

outputs: — o retorno

exit-code, reports-dir e report. Permite que o passo seguinte leia o resultado com steps.scan.outputs.exit-code.

branding:

Ícone e cor no GitHub Marketplace. Puramente cosmético.

runs: — o corpo da função

Cinco passos, nesta ordem:

  1. cache — calcula em bash se o cache do Trivy deve ser usado e com qual chave. dockerfile-lint e secret-scan pulam, porque Hadolint e Betterleaks nunca leem o banco de CVEs.
  2. Restore the Trivy database — actions/cache/restore@v6.
  3. scan — chama bash "$GITHUB_ACTION_PATH/src/run-scanner.sh". É aqui que o trabalho acontece. Todo o resto é entrada e saída.
  4. Save the Trivy database — actions/cache/save@v6, em um passo próprio; o motivo está em Decisões.
  5. Upload security reports — actions/upload-artifact@v7 sob always(): os relatórios sobem como artifact mesmo quando o scan falha.

O detalhe que vale internalizar

No bloco env: do passo scan:

env:
  ARK_IN_TRIVY_SEVERITY: ${{ inputs.trivy-severity }}
  ARK_IN_IMAGE:          ${{ inputs.image }}

Os inputs não são interpolados dentro do texto do script. Eles chegam como variáveis de ambiente com prefixo ARK_IN_.

Por quê

Se um input fosse colado direto no corpo do script — run: docker run ... ${{ inputs.image }} — um valor como "; rm -rf / # viraria comando. Passando por env:, ele é sempre apenas um valor. É o mesmo raciocínio de prepared statements contra SQL injection, e é uma classe de bug real e frequente em GitHub Actions.

The front end: action.yml

A composite Action is an Action made of other Actions and shell commands, with no compiled code.

When someone writes uses: Tooark/action-security-scanner@v{{COMPONENT_VERSION}}, GitHub downloads this repository and runs the steps declared here inside the caller's job. The file has four blocks.

inputs: — the parameters

There are 45, each with a description and a default. Think of them as the library's public function signature: it is the contract with consumers, and changing it breaks people. 

trivy-severity:
  description: "Severities included in the report, e.g. CRITICAL,HIGH."
  required: false
  default: ""

Most of them are default: "". That is not laziness — it is the precedence rule, explained under Decisions.

outputs: — the return value

exit-code, reports-dir and report. They let the next step read the result with steps.scan.outputs.exit-code.

branding:

Icon and colour on the GitHub Marketplace. Purely cosmetic.

runs: — the function body

Five steps, in this order:

  1. cache — works out in bash whether the Trivy cache should be used and under which key. dockerfile-lint and secret-scan skip it, because Hadolint and Betterleaks never read the CVE database.
  2. Restore the Trivy database — actions/cache/restore@v6.
  3. scan — calls bash "$GITHUB_ACTION_PATH/src/run-scanner.sh". This is where the work happens. Everything else is input and output.
  4. Save the Trivy database — actions/cache/save@v6, in a step of its own; the reason is under Decisions.
  5. Upload security reports — actions/upload-artifact@v7 under always(): the reports are uploaded as an artifact even when the scan fails.

The detail worth internalising

In the env: block of the scan step:

env:
  ARK_IN_TRIVY_SEVERITY: ${{ inputs.trivy-severity }}
  ARK_IN_IMAGE:          ${{ inputs.image }}

Inputs are not interpolated into the text of the script. They arrive as environment variables prefixed with ARK_IN_.

Why

If an input were pasted straight into the script body — run: docker run ... ${{ inputs.image }} — a value like "; rm -rf / # would become a command. Passing through env:, it is always just a value. It is the same reasoning as prepared statements against SQL injection, and it is a real, frequent class of bug in GitHub Actions.

06

O motor: src/run-scanner.sh

Umas 310 linhas de bash que traduzem os inputs — 35 variáveis ARK_IN_* — e o ambiente do job em um docker run. Quase todo comentário nele documenta um bug que alguém já sofreu.

O caminho completo de uma execução

  1. 1
    workflow do time uses: ...@v{{COMPONENT_VERSION}} with: command, image
  2. 2
    action.yml inputs → ARK_IN_* restaura o cache
  3. 3
    run-scanner.sh monta o docker run só o que não é vazio
  4. 4
    ark-tools Trivy · Hadolint Betterleaks
  5. 5
    saída scan-reports/ exit code → o gate
host do runner dentro do container · uid 1000 · workspace montado em /workspace

Os passos 1 a 3 rodam no host do runner; só o 4 roda dentro do container, que não herda o ambiente do job. Tudo o que ele lê — inputs, variáveis de env:, segredos — é o passo 3 que entrega.

O que o script faz, em ordem

Valida o comando contra uma lista fixa de sete. Nenhum input vira comando arbitrário.

Monta os volumes — o workspace vai para /workspace, os relatórios para /reports, o cache do Trivy para /home/app/.cache/trivy.

Reescreve caminhos. Quem escreve path: src/ está falando do disco do runner, mas o container enxerga /workspace/src. A função to_container_path faz essa tradução e deixa URLs e caminhos absolutos passarem intactos.

Encaminha os inputs que têm valor. Esta função é a primeira metade da regra de precedência do projeto inteiro: 

add_env() {
  local name="$1" value="$2"
  [ -n "$value" ] || return 0     # ← input vazio não é encaminhado
  DOCKER_ARGS+=(-e "$name=$value")
  FORWARDED+="$name"$'\n'         # ← e o que foi decidido fica anotado
  log "  $name=$value"
}

Diz à imagem quem ela é. O relatório registra qual imagem fez o scan, mas a imagem só conhece a própria versão de build. O nome e a tag com que ela rodou — um mirror, a tag flutuante {{SCANNER_VERSION}} — e o digest que essa tag resolveu, só quem chama sabe. O script passa ARK_IMAGE_NAME, ARK_IMAGE_TAG e ARK_IMAGE_DIGEST, e o relatório passa a apontar para nome@sha256:…, que é imutável. Se o job definir alguma das três em env:, ela prevalece.

Monta os argumentos por comando. Cada um dos sete tem uma forma diferente. Um exemplo de cuidado com usabilidade: em full-scan, se você não passou imagem nenhuma, o script liga FULL_SCAN_SKIP_IMAGE=true sozinho, em vez de deixar o Trivy falhar tentando escanear uma string vazia.

Repassa o ambiente do job, por nome. O docker run sobe o container sem o ambiente do runner, então uma variável que o workflow define em env: só chega às ferramentas se o script a repassar. É o que pass_job_env faz, e é a segunda metade da precedência: percorre o ambiente do passo e repassa toda variável TRIVY_*, HADOLINT_*, BETTERLEAKS_*, SBOM_*, FULL_SCAN_* e REPORT_* que não esteja vazia nem anotada em FORWARDED. Entram aí a configuração cujo input ficou em branco e as variáveis que não têm input, como TRIVY_SKIP_DB_UPDATE ou REPORT_METHOD. Roda por último de propósito: nesse ponto FORWARDED já tem tudo o que um input decidiu, além de REPORT_DIR, TRIVY_CACHE_DIR e FULL_SCAN_PATH, que são caminhos de dentro do container e ficam sempre com o script. 

DOCKER_ARGS+=(-e "$name=$value")   # add_env: um input, com o valor
DOCKER_ARGS+=(-e "$name")          # pass_job_env: env do job, só o nome

Segredos vêm do ambiente, nunca de inputs. TRIVY_TOKEN, REPORT_TOKEN, credenciais de registry e afins caem nesses mesmos prefixos e fazem o mesmo caminho. Passados só pelo nome, é o Docker que lê o valor do processo do script: ele não aparece na linha de comando do docker run, onde outro processo no runner poderia lê-lo, nem no log, que imprime apenas os nomes. Fora dos seis prefixos, só atravessa o que o script nomeia um a um — metadados do GitHub como GITHUB_SHA e GITHUB_REPOSITORY, e a identidade da imagem. GITHUB_TOKEN não está nessa lista, nem uma credencial de cloud que por acaso esteja definida no job.

Armadilha

Valores de input vão para o log do workflow — o add_env imprime cada NOME=valor que encaminha — e para a linha de comando do docker run. Um token passado como input é um token vazado.

Devolve a posse dos arquivos. A imagem roda como usuário não-root (uid 1000), que não é o usuário do runner. Sem o chown de volta no fim, o passo de upload de artifact não conseguiria ler os relatórios que o scanner acabou de escrever.

The engine: src/run-scanner.sh

About 310 lines of bash that translate the inputs — 35 ARK_IN_* variables — and the job environment into a docker run. Almost every comment in it documents a bug someone already hit.

The full path of one run

  1. 1
    the team's workflow uses: ...@v{{COMPONENT_VERSION}} with: command, image
  2. 2
    action.yml inputs → ARK_IN_* restores the cache
  3. 3
    run-scanner.sh builds the docker run only what is non-empty
  4. 4
    ark-tools Trivy · Hadolint Betterleaks
  5. 5
    output scan-reports/ exit code → the gate
the runner host inside the container · uid 1000 · workspace mounted at /workspace

Steps 1 to 3 run on the runner host; only step 4 runs inside the container, which does not inherit the job environment. Everything it reads — inputs, env: variables, secrets — is handed over by step 3.

What the script does, in order

Validates the command against a fixed list of seven. No input ever becomes an arbitrary command.

Sets up the volumes — the workspace goes to /workspace, the reports to /reports, the Trivy cache to /home/app/.cache/trivy.

Rewrites paths. Someone writing path: src/ means the runner's disk, but the container sees /workspace/src. The to_container_path function does that translation and lets URLs and absolute paths through untouched.

Forwards the inputs that carry a value. This function is the first half of the precedence rule of the whole project: 

add_env() {
  local name="$1" value="$2"
  [ -n "$value" ] || return 0     # ← an empty input is not forwarded
  DOCKER_ARGS+=(-e "$name=$value")
  FORWARDED+="$name"$'\n'         # ← and what was decided is written down
  log "  $name=$value"
}

Tells the image who it is. The report records which image ran the scan, but the image only knows its own build version. The name and tag it ran under — a mirror, the floating {{SCANNER_VERSION}} tag — and the digest that tag resolved to are known only to the caller. The script passes ARK_IMAGE_NAME, ARK_IMAGE_TAG and ARK_IMAGE_DIGEST, and the report then points at name@sha256:…, which is immutable. If the job sets any of the three in env:, that value wins.

Builds the arguments per command. Each of the seven has a different shape. One example of care for usability: in full-scan, if you passed no image at all, the script turns on FULL_SCAN_SKIP_IMAGE=true itself rather than letting Trivy fail trying to scan an empty string.

Passes the job environment on, by name. docker run starts the container without the runner's environment, so a variable the workflow sets with env: reaches the tools only if the script passes it on. That is what pass_job_env does, and it is the second half of the precedence rule: it walks the step's environment and passes on every TRIVY_*, HADOLINT_*, BETTERLEAKS_*, SBOM_*, FULL_SCAN_* and REPORT_* variable that is neither empty nor written down in FORWARDED. That covers a setting whose input was left blank and the variables that have no input at all, such as TRIVY_SKIP_DB_UPDATE or REPORT_METHOD. It runs last on purpose: by then FORWARDED holds everything an input decided, plus REPORT_DIR, TRIVY_CACHE_DIR and FULL_SCAN_PATH, which are paths inside the container and always stay with the script. 

DOCKER_ARGS+=(-e "$name=$value")   # add_env: an input, with its value
DOCKER_ARGS+=(-e "$name")          # pass_job_env: job env, the name only

Secrets come from the environment, never from inputs. TRIVY_TOKEN, REPORT_TOKEN, registry credentials and friends fall under those same prefixes and take the same route. Passed by name only, it is Docker that reads the value from the script's process: it shows up neither in the command line of docker run, where another process on the runner could read it, nor in the log, which prints only the names. Outside the six prefixes, only what the script names one by one crosses over — GitHub metadata such as GITHUB_SHA and GITHUB_REPOSITORY, and the image identity. GITHUB_TOKEN is not on that list, and neither is a cloud credential that happens to be set in the job.

Trap

Input values go to the workflow log — add_env prints every NAME=value it forwards — and to the command line of docker run. A token passed as an input is a leaked token.

Hands file ownership back. The image runs as a non-root user (uid 1000), which is not the runner user. Without the chown at the end, the artifact upload step could not read the reports the scanner had just written.

Versão única e testes de contrato

A parte que mais ensina, e o padrão mais transferível deste repositório para qualquer outro projeto.

O problema

A versão do scanner é pinada em dois lugares — o default de scanner-version no action.yml e o fallback dentro do run-scanner.sh — e a versão da própria Action aparece em todo trecho de copiar e colar: os dois READMEs, o SUPPORTED-INTEGRATIONS.md, os quatro exemplos e este guia. Atualizar de {{SCANNER_VERSION}} para 2.0 e esquecer o fallback, ou lançar uma versão e deixar um exemplo apontando para a anterior, não quebra nada na hora. YAML e Markdown não têm compilador; ninguém percebe.

A solução

O VERSION é a constante única:

# Single source of truth for versions in this repository.
COMPONENT_VERSION={{COMPONENT_VERSION}}
SCANNER_IMAGE={{SCANNER_IMAGE}}
SCANNER_VERSION={{SCANNER_VERSION}}
REPORT_SCHEMA={{REPORT_SCHEMA}}
REPORT_VERSION={{REPORT_VERSION}}

Até este guia sai dele: as versões que você lê nesta página são preenchidas a partir do VERSION pelo scripts/render-docs.sh, no deploy.

E o scripts/check-sync.sh é o teste de contrato que falha o CI quando algo diverge. Ele verifica quatro invariantes:

  1. O action.yml e o src/run-scanner.sh pinam exatamente a imagem declarada em VERSION.
  2. Todo input declarado no action.yml é lido por algum passo, e todo ARK_IN_* que ele prepara é consumido pelo run-scanner.sh — e vice-versa.
  3. Todo input está documentado nos dois READMEs.
  4. Toda referência de copiar e colar nos docs e nos exemplos pina COMPONENT_VERSION, toda menção ao envelope do relatório cita REPORT_VERSION, e este guia não digita versão nenhuma à mão.
Por quê

O item 2 pega o bug mais chato deste tipo de projeto: você adiciona um input, documenta, e esquece de conectar uma das pontas. O input existe na documentação, o usuário passa o valor, e nada acontece. Silenciosamente. O item 3 pega o inverso: o input funciona, mas não existe para quem só lê o README. O script transforma os dois em CI vermelho.

O scripts/check-examples.py faz o equivalente para o que as pessoas copiam. Cada passo que chama a Action, nos arquivos de examples/ e nos blocos YAML dos dois READMEs, é conferido contra o action.yml: toda chave de with: é um input declarado, todo steps.<id>.outputs.<nome> lido é um output declarado, e command é um scan que o script aceita. O comentário no topo do arquivo dá a justificativa: o GitHub não rejeita um input que a Action nunca declarou — o workflow roda, imprime um aviso, e a configuração silenciosamente não faz nada.

E o tests/run-scanner.test.sh testa o motor sem Docker: coloca no PATH um docker de mentira que grava a linha de comando em vez de executá-la, roda o script e confere o que ele montou — precedência, o que é repassado e o que nunca é, reescrita de caminhos, soft-fail, os outputs. O que ele não cobre é a imagem em si; isso fica com o job self-scan do CI.

A regra prática

Ao adicionar um input

Toque nos quatro lugares, ou o check-sync.sh vai te avisar: o bloco inputs: do action.yml, o env: do passo scan como ARK_IN_*, o src/run-scanner.sh, e as tabelas de inputs dos dois READMEs.

Para rodar as validações localmente, antes de abrir o PR:

python3 -m pip install pyyaml

./scripts/check-sync.sh               # pins de versão, fiação dos inputs, docs
python3 scripts/check-examples.py     # exemplos e trechos dos READMEs batem com o action.yml
./tests/run-scanner.test.sh           # o docker run que a Action monta, sem Docker
shellcheck -s bash src/run-scanner.sh scripts/*.sh tests/*.sh

Single source of truth and contract tests

The part with the most to teach, and the most transferable pattern in this repository.

The problem

The scanner version is pinned in two places — the default of scanner-version in action.yml and the fallback inside run-scanner.sh — and the Action's own version shows up in every snippet people copy: both READMEs, SUPPORTED-INTEGRATIONS.md, the four examples and this guide. Updating from {{SCANNER_VERSION}} to 2.0 and forgetting the fallback, or cutting a release and leaving an example pointing at the previous one, breaks nothing on the spot. YAML and Markdown have no compiler; nobody notices.

The solution

VERSION is the single constant:

# Single source of truth for versions in this repository.
COMPONENT_VERSION={{COMPONENT_VERSION}}
SCANNER_IMAGE={{SCANNER_IMAGE}}
SCANNER_VERSION={{SCANNER_VERSION}}
REPORT_SCHEMA={{REPORT_SCHEMA}}
REPORT_VERSION={{REPORT_VERSION}}

Even this guide comes out of it: the versions you read on this page are filled in from VERSION by scripts/render-docs.sh at deploy time.

And scripts/check-sync.sh is the contract test that fails CI when anything diverges. It checks four invariants:

  1. action.yml and src/run-scanner.sh pin exactly the image declared in VERSION.
  2. Every input action.yml declares is read by one of its steps, and every ARK_IN_* it stages is consumed by run-scanner.sh — and the other way round.
  3. Every input is documented in both READMEs.
  4. Every copy-paste reference in the docs and the examples pins COMPONENT_VERSION, every mention of the report envelope names REPORT_VERSION, and this guide types no version by hand.
Why

Item 2 catches the nastiest bug in this kind of project: you add an input, document it, and forget to connect one of the ends. The input exists in the documentation, the user sets the value, and nothing happens. Silently. Item 3 catches the reverse: the input works, but does not exist for anyone who only reads the README. The script turns both into a red build.

scripts/check-examples.py does the equivalent for what people copy. Every step that calls the Action, in the files under examples/ and in the YAML blocks of both READMEs, is checked against action.yml: each with: key is a declared input, each steps.<id>.outputs.<name> it reads is a declared output, and command names a scan the script accepts. The comment at the top of the file gives the justification: GitHub does not reject an input the Action never declared — the workflow runs, prints a warning, and the setting silently does nothing.

And tests/run-scanner.test.sh tests the engine without Docker: it puts a stand-in docker on the PATH that records the command line instead of running it, runs the script and asserts on what it built — precedence, what is forwarded and what never is, path rewriting, soft-fail, the outputs. What it cannot cover is the image itself; that is left to the self-scan job in CI.

The practical rule

When adding an input

Touch all four places, or check-sync.sh will tell you: the inputs: block of action.yml, the env: of its scan step as ARK_IN_*, src/run-scanner.sh, and the input tables of both READMEs.

To run the validations locally, before opening the PR:

python3 -m pip install pyyaml

./scripts/check-sync.sh               # version pins, input wiring, docs
python3 scripts/check-examples.py     # examples and README snippets match action.yml
./tests/run-scanner.test.sh           # the docker run the Action builds, without Docker
shellcheck -s bash src/run-scanner.sh scripts/*.sh tests/*.sh

O CI do próprio projeto

Uma dobra que confunde no começo: a pasta .github/workflows/ não tem nada a ver com o que o projeto entrega. É o CI deste repositório, como qualquer outro projeto tem.

ci.yml — roda em push e pull request

Job lint: parseia todo YAML do repositório, roda o check-sync.sh e o check-examples.py, roda os testes do script (tests/run-scanner.test.sh), o shellcheck (linter de bash) e o actionlint (linter de GitHub Actions).

Job self-scan: depois do lint, o projeto escaneia a si mesmo com a própria Action (uses: ./), em dois passos — um secret-scan e um filesystem-scan. Isso é dogfooding e funciona como teste de integração: é o único ponto em que a imagem de verdade roda, e se a Action estiver quebrada, o próprio CI quebra.

Duas linhas valem atenção:

permissions:
  contents: read     # o token do job só lê — menor privilégio
uses: docker://rhysd/actionlint@sha256:b1934ee5...   # pinado por digest
Por quê

Uma tag Docker (:1.7.12) pode ser reapontada pelo dono da imagem a qualquer momento. Um digest SHA-256 é imutável. Como esse container de terceiro roda dentro do CI deste projeto, pinar por digest impede que código não revisado passe a rodar aqui sem nenhum commit.

release.yml — roda ao dar push em uma tag v*.*.*

Roda de novo as validações e os testes, confere se a tag bate com COMPONENT_VERSION — tag v1.0.1 com VERSION=1.0.0 é release recusada —, cria o GitHub Release com notas geradas e move as tags flutuantes.

Referência Aponta para Quando usar
v{{COMPONENT_VERSION}} Exatamente aquele release Pipeline reproduzível
v{{COMPONENT_MINOR}} Último patch da linha {{COMPONENT_MINOR}} Patches automáticos
v{{COMPONENT_MAJOR}} Último release da linha {{COMPONENT_MAJOR}}.x Minors e patches automáticos
main Trabalho não lançado Nunca em um pipeline que te importa

É a convenção do ecossistema de Actions — actions/checkout@v7 funciona assim. O README é honesto sobre o custo: pinar v{{COMPONENT_MAJOR}} significa rodar, depois do próximo release, código que você não revisou.

dependabot.yml

Abre um PR semanal atualizando as Actions referenciadas. O comentário no arquivo fecha o raciocínio do digest: sem isso, pinar congelaria a dependência em vez de controlá-la. Pinar sem um mecanismo de atualização não é segurança, é dívida.

The project's own CI

A fold that confuses at first: the .github/workflows/ folder has nothing to do with what the project delivers. It is this repository's CI, like any other project has.

ci.yml — runs on push and pull request

Job lint: parses every YAML file in the repository, runs check-sync.sh and check-examples.py, runs the tests of the script (tests/run-scanner.test.sh), shellcheck (a bash linter) and actionlint (a GitHub Actions linter).

Job self-scan: after lint, the project scans itself with its own Action (uses: ./), in two steps — a secret-scan and a filesystem-scan. That is dogfooding, and it works as an integration test: it is the only place the real image runs, and if the Action is broken, this repository's own CI breaks.

Two lines are worth noticing:

permissions:
  contents: read     # the job token only reads — least privilege
uses: docker://rhysd/actionlint@sha256:b1934ee5...   # pinned by digest
Why

A Docker tag (:1.7.12) can be repointed by the image owner at any moment. A SHA-256 digest is immutable. Since that third-party container runs inside this project's CI, pinning by digest stops unreviewed code from starting to run here without a single commit.

release.yml — runs when a v*.*.* tag is pushed

Runs the validations and the tests again, checks that the tag agrees with COMPONENT_VERSION — tag v1.0.1 with VERSION=1.0.0 is a refused release — creates the GitHub Release with generated notes, and moves the floating tags.

Reference Resolves to Use when
v{{COMPONENT_VERSION}} Exactly that release Reproducible pipelines
v{{COMPONENT_MINOR}} Newest patch of the {{COMPONENT_MINOR}} line Automatic patch updates
v{{COMPONENT_MAJOR}} Newest release of the {{COMPONENT_MAJOR}}.x line Automatic minor and patch updates
main Unreleased work Never in a pipeline you care about

It is the Actions ecosystem convention — actions/checkout@v7 works this way. The README is honest about the cost: pinning v{{COMPONENT_MAJOR}} means running code you have not reviewed after the next release.

dependabot.yml

Opens a weekly PR updating the referenced Actions. The comment in the file closes the digest reasoning: without it, pinning would freeze the dependency instead of controlling it. Pinning without an update mechanism is not security, it is debt.

Decisões e armadilhas

As escolhas que parecem estranhas na primeira leitura, e o motivo de cada uma. Esta seção é a que mais economiza tempo quando algo dá errado.

A regra de precedência — o motivo dos default: "" 

input  >  env do job ou do passo  >  default da imagem

Input vazio nunca é encaminhado. Isso permite que um workflow defina TRIVY_SEVERITY uma vez em um env: de topo e deixe o input em branco em todos os jobs, em vez de repetir. Definindo os dois, o input ganha.

Se o input vazio fosse encaminhado, ele sobrescreveria a variável do env: com string vazia e quebraria esse padrão. É a diferença entre undefined e "". Duas funções do run-scanner.sh sustentam a regra juntas: add_env() não encaminha input vazio e anota cada nome que decidiu; pass_job_env() repassa do ambiente do job, por nome, o que não está anotado. A segunda metade é a fácil de esquecer: o container não herda o ambiente do runner, e sem ela o nível do meio existe só na documentação.

O cache do Trivy, e o passo de save separado

O banco de CVEs do Trivy é grande. Baixá-lo a cada build é a parte mais lenta do scan e o jeito mais fácil de bater o rate limit do registry. A Action guarda o banco em RUNNER_TEMP e usa actions/cache com uma entrada por dia por versão do scanner, com fallback para o dia anterior — assim o Trivy atualiza um banco existente em vez de baixar um inteiro.

A sutileza que explica o passo extra

O actions/cache normal salva em um post step, e post steps são pulados quando um passo anterior falhou. Mas esta Action falha por design quando encontra vulnerabilidade. Sem o passo de save separado, só repositórios que não acham nada populariam o cache — justamente os que menos precisam.

fetch-depth: 0

Por padrão, o actions/checkout faz shallow clone (só o último commit) porque é mais rápido. Mas o Betterleaks procura segredos no histórico — e o caso clássico é exatamente a chave commitada e “removida” depois.

Falha silenciosa

Com clone raso, o Betterleaks não vê quase nada e não reclama. O job passa verde e você acha que está protegido. Por isso todo exemplo que roda o Betterleaks — secret-scan ou full-scan — faz o checkout com fetch-depth: 0.

docker-socket: "true" entrega root no runner

Montar /var/run/docker.sock dá ao container controle total do daemon Docker do host — ele pode subir um container privilegiado e ler a máquina inteira. Vem desligado. Só é necessário para escanear uma imagem construída no mesmo job; imagem já enviada a um registry não precisa. Em runner self-hosted compartilhado, a recomendação é empurrar para o registry e escanear de lá.

Relatórios podem conter os segredos que encontraram

Duas configurações transformam um artifact em vazamento: betterleaks-redact: "0" escreve os segredos detectados em texto claro, e adicionar secret a trivy-scanners coloca os achados do Trivy no relatório. Artifacts são baixáveis por qualquer um com acesso de leitura ao repositório. O default é redação de 100%, e o log imprime apenas regra, arquivo, linha e commit curto — nunca o segredo.

Propriedade de arquivos no runner

A imagem roda como uid 1000, que não é o usuário do runner. O script cria o diretório de relatórios com permissão ampla durante o scan, devolve a posse no fim e fecha as permissões de volta; o workspace é declarado como safe directory do git por variável de ambiente. Em runner efêmero isso é irrelevante; em self-hosted com jobs concorrentes, existe uma janela curta em que outro job poderia escrever ali.

Duas pegadinhas menores

  • dockerfile-lint processa um arquivo por passo. Para vários, use full-scan com dockerfiles: "a,b,c", ou rode o dockerfile-lint uma vez por arquivo.
  • O nome do artifact precisa ser único na execução do workflow. Cada execução da Action sobe o diretório de relatórios com o nome de artifact-name, e um segundo upload com o mesmo nome falha. Quando a Action roda mais de uma vez, no mesmo job ou em jobs diferentes, dê um artifact-name a cada passo.

Decisions and traps

The choices that look strange on a first read, and the reason behind each. This is the section that saves the most time when something goes wrong.

The precedence rule — why default: "" everywhere 

input  >  env of the job or step  >  image default

An empty input is never forwarded. That lets a workflow set TRIVY_SEVERITY once in a top-level env: and leave the input blank in every job, instead of repeating it. Set both and the input wins.

If an empty input were forwarded, it would overwrite the env: variable with an empty string and break that pattern. It is the difference between undefined and "". Two functions in run-scanner.sh hold the rule up together: add_env() does not forward an empty input and writes down every name it decided; pass_job_env() passes on from the job environment, by name, whatever is not written down. The second half is the easy one to forget: the container does not inherit the runner's environment, and without it the middle tier exists only in the documentation.

The Trivy cache, and the separate save step

Trivy's CVE database is large. Downloading it on every build is the slowest part of a scan and the easiest way to hit a registry rate limit. The Action keeps the database in RUNNER_TEMP and uses actions/cache with one entry per day per scanner version, falling back to the previous day — so Trivy refreshes an existing database instead of fetching a whole one.

The subtlety that explains the extra step

The normal actions/cache saves in a post step, and post steps are skipped when an earlier step failed. But this Action fails by design when it finds a vulnerability. Without the separate save step, only repositories that find nothing would ever populate the cache — precisely the ones that need it least.

fetch-depth: 0

By default actions/checkout does a shallow clone (only the last commit) because it is faster. But Betterleaks looks for secrets in the history — and the classic case is exactly the key that was committed and “removed” afterwards.

Silent failure

With a shallow clone, Betterleaks sees almost nothing and does not complain. The job passes green and you believe you are protected. That is why every example that runs Betterleaks — secret-scan or full-scan — checks out with fetch-depth: 0.

docker-socket: "true" hands over root on the runner

Mounting /var/run/docker.sock gives the container full control of the host's Docker daemon — it can start a privileged container and read the whole machine. It is off by default. It is only needed to scan an image built in the same job; an image already pushed to a registry does not need it. On a shared self-hosted runner, the recommendation is to push to the registry and scan from there.

Reports can contain the secrets they found

Two settings turn an artifact into a disclosure: betterleaks-redact: "0" writes detected secrets in cleartext, and adding secret to trivy-scanners puts Trivy's findings in the report. Artifacts are downloadable by anyone with read access to the repository. The default is 100% redaction, and the log prints only rule, file, line and short commit — never the secret.

File ownership on the runner

The image runs as uid 1000, which is not the runner user. The script creates the reports directory with broad permissions during the scan, hands ownership back at the end and tightens the permissions again; the workspace is declared a git safe directory through environment variables. On an ephemeral runner this is immaterial; on a self-hosted one with concurrent jobs there is a short window in which another job could write there.

Two smaller gotchas

  • dockerfile-lint handles one file per step. For several, use full-scan with dockerfiles: "a,b,c", or run dockerfile-lint once per file.
  • Artifact names must be unique in a workflow run. Every run of the Action uploads the reports directory under artifact-name, and a second upload with the same name fails. When the Action runs more than once, in one job or across jobs, give each step its own artifact-name.
